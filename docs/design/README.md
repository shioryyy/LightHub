# LightHub 产品与工程方案

方案版本：1.1。决策日期：2026-09-11（初版 2026-09-08）。状态：**已确定的设计基线，待分阶段实现与验收**。

本方案根据维护者“敲定事项并形成周密材料”的要求形成。它同时适用于从零实现和现有代码的增量演进；采用何种施工方式不改变产品契约。本次只更新文档，没有启动新工程、重写程序、修改设备或发布软件。

## 1. 定位与成功标准

LightHub 是面向多型号、跨平台的开源 Logitech HID++ 游戏鼠标配置工具。核心体验是：识别设备、明确修改对象、配置板载功能、验证保存、退出软件。成功标准是设置可预测、保存可信、失败可恢复，而非 G HUB 功能数量对齐。

用户反馈支持简化板载工作流，也存在需要固定软件宏和可靠应用切换的用户。当前调研是有限的历史讨论，不能推导多数用户比例。首版选择板载优先是产品决策，不是假定所有用户需求相同。调研依据保留在[历史研究](../PRODUCT-STRATEGY.md)中。

LightHub 默认提供离线、板载优先的配置体验，已支持的板载功能不依赖常驻进程。宏编辑独立于执行方式；设备支持且经过验证时，可写入板载执行。计划提供由用户主动启用的软件宏运行器，固定配置可独立使用，按应用自动切换单独启用且默认关闭。默认不安装系统服务、不自启、不进行全局输入监听；额外权限按功能申请。各版本明确列出实际支持范围。

## 2. 已确定的关键决策

| 编号 | 决策 | 约束与理由 |
| --- | --- | --- |
| D01 | 首要服务配置后即可退出的鼠标用户 | 普通按键与已验证板载宏不依赖常驻程序 |
| D02 | 板载优先，启动和重连只读 | 不因打开软件而强制切换设备模式 |
| D03 | 编辑、保存、启用、临时试用独立 | 保存备用槽不默认启用它；保存按键不默认重置当前 DPI 档位 |
| D04 | 默认固定配置；可选软件宏运行器与应用自动切换分别启用 | 运行器是规划能力，先验证 GPW1/Windows 触发机制；默认无系统服务、自启、全局监听；应用切换不是软件宏前置条件 |
| D05 | 使用 .NET 10、C#、Avalonia、HidSharp | 初始依赖沿用已构建验证的 Avalonia 12.1.2、HidSharp 2.6.4；按发布批次维护 |
| D06 | 核心逻辑、应用编排、传输、界面分层 | 不用按键图、型号名称或 UI 状态决定协议写权限 |
| D07 | 支持状态按操作、型号、固件、连接方式、平台分别记录 | 识别、读取、临时设置、板载写入、恢复不能共用一个总开关 |
| D08 | 宏是核心编辑能力，首批为有界单次键盘序列；编辑、板载执行、软件执行分离 | 本地编辑无需执行后端；板载写入须先有恢复和物理证据；软件执行须先有触发与停止证据；循环、录制、脚本后置 |
| D09 | 本地预设、设备快照、草稿、运行状态分开 | 预设可移植，原始备份绑定物理设备 |
| D10 | 使用版本化 JSON 和原子写入 | 首版不引入数据库、可执行插件系统或跨进程 RPC |
| D11 | 持久写入必须备份、冲突检查、日志记录、完整回读 | 不因追求即时手感取消验证或静默重试闪存写入 |
| D12 | 临时 DPI 不写闪存，拥有独立试用生命周期 | 退出试用尝试恢复；断连或所有权不明时不盲目回写 |
| D13 | 自动备份开启；自动清理关闭 | 手动清理默认保留每台设备最近 10 份，保护未完成事务、置顶和手动里程碑 |
| D14 | 普通删除可恢复 | 普通删除进入本地回收区；永久删除需独立确认；现有备份回收实现仍需按平台验收 |
| D15 | 核心运行离线，无账号、遥测、自动更新或开机自启 | 更新经用户主动下载安装，不在迁移时向设备写配置 |
| D16 | 三平台共用架构，发布质量按平台单独标注 | 优先 Windows 实机闭环；Linux/macOS 不因交叉编译成功获得写入支持 |
| D17 | MIT 开源，保留第三方来源与许可证清单 | 设备资料可作为证据，不能直接把其他项目的兼容列表等同于本项目兼容 |
| D18 | 先完成行为契约与恢复闭环，再扩展设备功能 | 功能缺口本身不是全部重写或更换框架的理由 |

## 4. 决策不等于验证

1.0 冻结时的历史基线为 `0.2.0-alpha.1` 加未发布迭代及当时记录的 61 项测试。1.1 修订时仓库声明版本为 `0.3.0-alpha.1`；本次为文档与代码边界核对，没有重新执行测试或硬件验证。Windows GPW1 基础非活动配置写入/恢复及临时 DPI 的已有证据仍以验证报告为准。宏、G-Shift、新模式语义、完整物理按键验收和其他平台实机行为没有因此通过验证。

目前只有一台 GPW1 可供本地验证。其他型号通过贡献者报告和测试设备逐步推进；没有证据就不开放该操作。发布计划不设虚构完成日期，不以交叉编译、模拟测试或别人的驱动替代实机证据。

技术与行为选择已经确定，剩下的是执行和证据门槛。若实测证明某个选择不可行，按决策变更流程修订，不把它悄悄降格成“可选”。

## 5. 与已有文档及代码的关系

本文档集是新开发工作的规范来源。`PRODUCT-STRATEGY.md` 保留为研究与提案历史；`GHUB-GAP-ANALYSIS.md` 是差距清单，不是强制实现全部 G HUB 功能的需求。`ARCHITECTURE.md` 和验证报告描述现有实现，不代表目标设计已落地。

若范围或质量门槛发生冲突，以本文档集为准；已有测试、备份兼容和安全约束仍须保留。旧 `PLAN.md` 中“三平台共同达到稳定”的笼统表述，由本方案的按平台、按功能独立质量等级取代，且降低任何公开支持等级必须明确公告。

变更 D01—D18 中的决定时，必须记录原因、用户行为变化、替代方案、数据兼容、验证证据和关联验收项，更新方案版本。发现风险可以暂停开放功能，不能绕过门槛继续发布。

## 6. 后续执行方式

在现有仓库增量演进，不重新搭建工程。M0—M6 的已完成程度以验证报告为准，不因方案修订清零。宏下一批任务为 [E1 本地宏模型/存储、E2 离线编辑器与 T0 触发可行性验证](06-macros-and-runtime.md)，各自验收，不等待板载宏写入完成。当前修订不改变设备写权限，也不宣称规划能力已实现。
